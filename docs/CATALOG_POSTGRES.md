## Что реализовано

В явном `CRM_BACKEND=postgres` существующие экраны используют новую базу. Legacy GAS не удалён и не переключён; данные из рабочей таблицы не импортировались. Staging/production не изменялись.

| Действие                             | Поведение                                                                                                            |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `createBranch`                       | Имя, адрес, IANA timezone; создание, аудит и подтверждение в одной транзакции                                        |
| `createClient`                       | Карточка с нулевыми оплатами/остатками; строгий DTO; долговечный повтор                                              |
| `updateClient`                       | Разрешённые поля, обязательная expectedVersion, увеличение версии, аудит                                             |
| `deleteClient`                       | Только действительно пустая карточка; проверка всех связей и учётных значений                                        |
| `getClients`, `getSubscriptionsPage` | Поиск, статус, сортировка, страницы, полный total и hasMore                                                          |
| `getSheet`                           | Безопасные филиалы, тренеры и ограниченный список клиентов; не больше 500 карточек, иначе явное требование пагинации |
| `searchClientOptions`                | Только активные, фильтр секции, допустимый филиал, ограниченный ответ                                                |
| `createCoach`                        | Профиль с аккаунтом или без; профиль, credential, филиал/membership и аудит атомарны                                 |
| `deleteCoach`                        | Логическое удаление через archivedAt, отключение связанного аккаунта и отзыв сессий; история и ID сохраняются        |
| Управление аккаунтом/привязка        | Сервисы этапа 4 сохраняются; нельзя активировать архивированный профиль обычной кнопкой                              |
| `getClientHistory`                   | Реальные подтверждённые платежи/журнал и read-only сверка; не выдуманные пустые записи                               |

Публичный модуль расписания и посещаемости **ещё не перенесён**. Старое чтение bootstrap конкретных строк не является реализацией этапов 6–7. `getSheet(Расписание)` и неподключённые операции отказывают явно, без запроса к GAS.

## Данные, версии и повторы

Пятая миграция добавляет `clients.version` с положительным целочисленным ограничением и `coaches.specialty`. Всего пять миграций и прежние 21 модель; старые миграции не переписывались. Новые поля добавлены с совместимыми defaults. Миграция применена только к изолированному Local; каждый тест получает свежую одноразовую базу.

Версия карточки возвращается в администраторском списке и передаётся существующими формами изменения, архивации, восстановления и удаления. Несовпадение — CONFLICT, без записи. Нагрузка и категория описывают следующий тариф и не пересчитывают оплаченные занятия.

Исправлен нюанс Zod defaults: частичное `updateClient(status=Архив)` не подставляет категорию «плавание» и нагрузку 1 от схемы создания. Проверяется отдельным тестом. Возраст/инициалы вычисляются сервером, дата рождения хранится как DATE и выдаётся `ДД.ММ.ГГГГ`.

`MutationRequest` уникален по actorId/requestId. Fingerprint — HMAC семантического payload, не открытый password hash. Авторизация проверяется заново внутри транзакции. Мутация, аудит и marker коммитятся вместе; отказ аудита откатывает создание и подтверждение. Маркеры immutable, ссылка на созданную сущность хранится в дочернем аудите. Персональные данные и пароли в журнал не копируются.

Повтор создания с тем же ключом возвращает прежний ID и текущее состояние; другой payload даёт CONFLICT. Старое редактирование не отменяет более новую правку. Удалённый клиент/архивированный тренер не восстанавливается поздним повтором создания. Физическое удаление клиента сохраняет подтверждения и аудит. Создание/изменение филиалов и профилей в store не добавляет одинаковый ID второй раз.

Frontend сохраняет неопределённую попытку создания тренера/филиала и изменения/удаления карточки **в памяти**, соединяет параллельные отправки и не разрешает изменённые данные под видом повтора. HTTP 408/5xx/потерянный или неполный success сохраняют ключ. Даже если список перечитан с новой версией, идентичное неподтверждённое редактирование отправляет первоначальную версию и ключ. Смена пользователя/выход очищают частное состояние. Восстановление этих административных черновиков после reload не реализовано: это не гарантия восстановления посещаемости из этапа 7.

## Права и приватность

Все изменения справочников — admin-only. Тренер не может изменить карточку/финансы/назначения или удалить тренера прямым API-запросом.

Канонический филиал тренера берётся из актуального аккаунта. Присланный branchId не расширяет чтение. В `getClients`, `getSheet(Клиенты)` и поиске ему возвращаются ID, имя ребёнка, филиал, статус, секция, инициалы и остаток занятий — без телефона, email, имени родителя, даты рождения, комментария, сумм, денежного баланса и квитанции. Поиск тренера не использует скрытые контакты; сортировка по оплате запрещена. Профили тренеров выдаются без credential/контактных полей.

Администратор получает нужные поля для текущего интерфейса. Серверный `canDelete` учитывает реальные связи; это лишь помощь интерфейсу, не замена повторной серверной проверки удаления. Денежные значения преобразуются в старый UI-формат только в безопасном целочисленном диапазоне; выход за пределы не теряет точность молча. Точный money API остаётся задачей учётного модуля.

## Первоначальная оплата не теряется

До подключения учётных записей API **не принимает** ненулевую первоначальную оплату: 422 VALIDATION с пояснением, карточка/платёж/marker не создаются. Указанная сумма не считается оплаченной и не выбрасывается молча. В PostgreSQL-форме поле оплаты отключено и объяснено; автоматическая подстановка тарифа выключена. После создания без оплаты остатки строго нулевые.

Рассчитанный старой формой `subscription` не передаётся в PostgreSQL, и сервер не принимает виртуальные остатки. Через обычный update нельзя менять branchId, оплаты, остатки, историю, служебные поля или состав группы. Первоначальный платёж следует реализовать вместе с учётом **в той же транзакции**, после чего явно включить ввод суммы. Нулевые остатки сейчас не означают право бесплатно начислять занятия для демонстрации.

История читает настоящие строки PostgreSQL и показывает несогласованный остаток как расхождение, а не придумывает платежи. Запись оплаты/корректировки, подтверждённый repair и полный финансовый модуль ещё не подключены.

## Запуск и проверка

На закреплённом Node 22 и с Docker-доступом:

```bash
npm run db:local:up
npm run db:migrate:local
# Если администратора ещё нет, выбрать собственные credentials в терминале:
npm run auth:bootstrap:local
npm run dev:postgres
```

После обновления схемы перезапустить собственный dev-процесс. Существующие реальные таблицы и другие сервисы не останавливаются автоматически. `npm run dev` по-прежнему legacy GAS.

Тесты PostgreSQL используют один выделенный тестовый порт: suites запускать **последовательно**, не параллельно. Конфликт порта завершает прогон до подключения и удаляет только его собственный контейнер; не разрешается подключаться к соседнему тесту.

```bash
npm run test:postgres
npm run test:auth:postgres
npm run test:domain:postgres
npm run release:check
# Chromium установлен через npx playwright install chromium:
npm run test:auth:browser
npm run security:secrets
```

CI дополнен domain-suite. Публичный GitHub workflow и deployment не запускались. Требования least-privilege БД, staging, backup/restore и закрытия существующих high предупреждений зависимостей остаются условиями будущего выпуска.

Итоговые успешные проверки:

- 256 unit/regression: прежние 253 + три frontend-теста безопасного создания, повторного редактирования с первоначальной версией и запрета виртуального subscription.
- 17 domain integration: справочники, нулевые начисления, запрет оплаты до учёта, приватность, версии, старые/параллельные повторы, запрет удаления непустой карточки, отсутствие восстановления удалённого/архивированного объекта, rollback при отказе аудита и совместимый порядок блокировок аккаунтов/профилей.
- 35 auth integration и 28 foundation на одноразовых базах; все пять миграций применяются с нуля и повторно.
- 10 сценариев реального production Next-сервера: прежние 4 HTTP + 4 browser и два новых browser-сценария полного CRUD клиента/создания филиала и создания тренера с потерянным ответом после коммита. Один профиль, один аккаунт и прежний ключ подтверждены запросами к БД.
- TypeScript, ESLint, Prettier, Webpack production build, secret scan и `git diff --check`.

Всего 346 проверок без двойного подсчёта HTTP-сценариев в browser suite. Проверки схемы выполнялись на новой пятой миграции; актуальные auth/domain/browser suites и release-check повторены после последних изменений кода. Конфликт порта при параллельном запуске безопасно остановил один технический прогон до подключения; итоговые прогоны выполнены последовательно и прошли.

## Что требуется для этапов 6–7

До реализации спорных прав нужен явный ответ владельца:

1. Тренер изменяет/отменяет только назначенные ему занятия или все занятия своего филиала (D-01a)?
2. Отмена занятия с уже записанными отметками запрещена или разрешена с транзакционным возвратом списаний (D-06)?
3. Какова допустимая давность исправлений прошлой посещаемости для тренера и требуется ли причина (D-07)?

Не выбранные пользователем варианты не считаются согласованием. Учебные данные, неполный backend и локальные проверки не являются разрешением переключать настоящих людей на PostgreSQL.
