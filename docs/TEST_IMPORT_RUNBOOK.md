# Постоянный тестовый импорт: операторская процедура

8 октября 2026 года. Только **Local**, исходник `База данных.xlsx`. Не переключает GAS/production и не импортирует рабочую CRM.

## Политика этого набора

После просьбы «доделай» выбран и озвучен безопасный вариант по умолчанию: четыре старых занятия остаются архивом без назначения тренеров и появления в рабочем календаре. Это консервативное допущение для тестового проекта, а не согласование новых прав или восстановление состава по имени тренера. Оригинальные строки и семь старых отметок сохраняются; повторного списания занятий нет. Для другого режима нужен отдельный явно согласованный план, не изменение уже записанного immutable batch.

Утверждённые ранее правила: `Europe/Moscow`, старые платежи исключены из активного учёта, новые платежи работают. Не создаём вымышленные платежи на 20 000 ₽ из старых карточек. Импорт сохраняет количественные остатки как подтверждённые opening credits. Старые пароли не переносятся: два coach-аккаунта отключены до контролируемого сброса и активации.

## Состояние до постоянной записи

Read-only проверка Local: девять миграций применены, аккаунтов/администраторов, клиентов, филиалов, занятий, документов и import batches нет. Поэтому постоянный apply пока **не выполнен**: его должен подтвердить существующий активный администратор. Создание первого администратора требует скрытого интерактивного ввода пароля пользователем; агент не подставляет известный пароль и не активирует аккаунт без учётных данных.

Создана приватная копия исходной пустой Local-базы, каталог проверен через `pg_restore --list`. Это не испытание восстановления и не резервирование production. После bootstrap нужно сделать новую копию уже с администратором перед импортом.

## Последовательность

Из корня `lotos_crm`, с работающим локальным Docker:

```bash
# Закреплённый Node.js 22 из проекта:
export PATH="$PWD/.tools/node/bin:$PATH"

# Пользователь вводит логин и пароль в своём терминале, пароль скрыт:
npm run auth:bootstrap:local

# Копия именно Local: фиксированные контейнер, база и loopback-порт.
npm run db:backup:local

# Без SQL-записи; проверяем количества и политику архива:
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08

# YOUR_ADMIN_LOGIN заменить реальным логином созданного администратора:
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08 --actor YOUR_ADMIN_LOGIN --apply

# Отдельная read-only SQL-сверка; успех — success:true, writes:0, issues:[]:
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08 --verify

# Повтор должен вернуть duplicate:true, без создания дублей/отката правок:
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08 --actor YOUR_ADMIN_LOGIN --apply
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08 --verify

npm run dev:postgres
```

Если администратор уже существует, не создавать второго: проверить его актуальные роль и статус и использовать его логин. Не присылать пароль в чат, не задавать его аргументом команды или в `.env`. Legacy `npm run dev` пока использует GAS; для просмотра результата нужен явный PostgreSQL-режим.

## Критерии приёмки этого файла

| Проверка                                                 | Ожидаемый результат                                                |
| -------------------------------------------------------- | ------------------------------------------------------------------ |
| SHA256 исходника                                         | `557b6ec1f5f607f9ee49615213cbd7bcbcb1936432f19deb451512b9626ab061` |
| Исходные строки / приватные архивные записи              | 25 / 25                                                            |
| Связанные исходные аккаунты                              | 3: существующий admin + 2 отключённых coach                        |
| Филиалы / карточки тренеров / клиенты                    | 1 / 1 / 3                                                          |
| Остатки по строкам клиентов 2, 3, 4                      | 2/4, 7/8, 6/8                                                      |
| Старые занятия в архиве / активном календаре             | 4 / 0                                                              |
| Архивные отметки                                         | 7, без новых списаний                                              |
| Выдуманные платежи / перенесённые старые password hashes | 0 / 0                                                              |
| Повтор исходного плана                                   | `duplicate:true`, прежний отчёт                                    |
| Другой план / namespace для того же источника            | `CONFLICT`, без частичной записи                                   |

Сверка проверяет архив, устойчивую карту ID, связи, opening credits и текущее согласование карточки с журналом. Для явно привязанных занятий также проверяются первоначальные дата/время, тренер и состав. Законные последующие изменения не должны заменяться данными XLSX. Отчёт показывает коды проблем и номера строк без персональных полей/паролей. Несовпадение не исправляется автоматически; `--verify` возвращает ненулевой exit code.

`--apply` и `--verify` запрещены одновременно. Writer и сверка допускают только изолированные Local/Test; этот операторский CLI намеренно Local-only. Источник и namespace нельзя менять ради обхода конфликта. Исходный XLSX, dump и raw-план не публикуются в Git. `.artifacts/local-before-import-*` содержит приватные копии с правами каталога 0700 и файлов 0600; скрипт не удаляет частичные копии при ошибке.

## Границы закрытия

Процедура проверена на одноразовом Test, включая предоставленный XLSX. Постоянный перенос закрывается **только после** bootstrap, новой копии, apply, успешной сверки и проверки повтора на Local. Пока bootstrap не выполнен, импорт остаётся подготовленным, но не выполненным.

Общий production-import повторяющихся серий, старых Drive-документов, переключение пользователей, staging и практическое восстановление внешних копий относятся к последующим согласованным работам. Карантин не является потерей данных, но и не является работающим расписанием прошлых занятий: история доступна администратору read-only.
