# Временный тестовый стенд на Vercel

Решение владельца 9 октября 2026 года: VPS ещё не арендован; временный стенд предлагается разместить на Vercel, позднее перенести на свой сервер. Создание постоянного Local-администратора агентом **отклонено**: владелец создаёт его вручную. Local-import, GAS и production этим решением не переключаются.

**Статус: облачные адаптеры, изолированный профиль и операторские команды реализованы и проходят локальную приёмку. Публичный deployment ещё не выполнен.** Доступ к Vercel/Neon не подтверждён; действующие БД/private store/HTTPS-ссылка не проверены. Ни локальная сборка, ни тестовый Blob-транспорт не заменяют реальную облачную приёмку. Этапы 12–13 не завершены.

## Что сохраняем

**Актуальное решение владельца: временный стенд запускаем без Private Vercel Blob.** В шаблоне `DOCUMENT_STORAGE=disabled`; загрузка, скачивание и восстановление квитанций выключены. Blob store/ключи/marker создавать не нужно. Оплаты, история платежей и посещаемость не отключаются. Blob-механизмы ниже — необязательный будущий вариант, не текущая инструкция подключения. Существующие документы и намерения не удаляются. Замена заблокированного Neon на Supabase обсуждена, но ещё не реализована в валидаторе: текущий cloud DB-профиль остаётся Neon, просто подставить Supabase URL нельзя.

Next.js, React, Prisma, Better Auth, Zod, бизнес-сервисы, транзакции, requestId, актуальные серверные права и существующие кабинеты остаются. Временное размещение не требует перехода на Supabase Auth или другого переписывания бизнес-логики.

На Vercel работает приложение и Node.js API, **не Docker Compose**. Caddy нужен для будущего VPS; в облачном варианте TLS предоставляет платформа. PostgreSQL размещается в отдельном изолированном managed-проекте. Файловое хранилище сейчас не подключаем: квитанции временно выключены. БД/публичный deployment пока не подключены. Старый Supabase-проект и предоставленный XLSX не используем автоматически: опубликованный тестовый набор должен быть вымышленным.

## Реализованная подготовка и оставшиеся проверки

1. **Изоляция БД — реализована.** `DEPLOY_TARGET=vercel` допускается только для `APP_ENV=staging`, точного Neon pooler hostname, БД `lotos_crm_staging` и роли `lotos_runtime`. Обязателен `sslmode=verify-full`. Миграции имеют отдельный direct endpoint/роль; Local/Test и self-hosted проверки не ослаблены.
2. **Пул — реализован, настоящая HTTP-сеть ещё не проверена.** Пул `pg` переиспользуется в процессе, cloud max=1, есть Vercel lifecycle integration и ограниченные ожидания. Миграции не запускаются при build/HTTP. Interactive transactions/locks, serverless cold start и реальный pooler требуют публичной приёмки. [Рекомендации Vercel](https://vercel.com/kb/guide/connection-pooling-with-functions).
3. **Документы — реализован private Blob adapter.** Фиксированные ключи, exclusive put, проверка URL/private store, размера и SHA-256; прежние SQL-намерения, версии, подтверждения и inbox восстановления сохраняются. Потерянный ответ подтверждается чтением первоначальных байтов. Неизвестный commit не удаляет файл. Тестовый транспорт проверен вместе с настоящим PostgreSQL; настоящий Blob ещё не подключён. Self-hosted filesystem остаётся прежним, `/tmp` как постоянное хранилище не используется.
4. **Размер — выбран явный cloud-предел 3 МиБ.** Self-hosted остаётся 5 МиБ. Сервер сообщает предел интерфейсу; проверяется размер до base64 и реальные байты API. Для 3 МиБ получается 4 194 304 байта base64, ограниченный JSON-конверт оставляет запас до платформенных 4.5 MB. Проверки содержимого PDF/изображений сохранены. [Лимиты Functions](https://vercel.com/docs/functions/limitations).
5. **Health/proxy — реализованы.** Readiness читает приватный marker и SQL, не создаёт объекты и не раскрывает детали. Marker создаётся отдельной операторской командой. IP принимается из `x-vercel-forwarded-for` только в явно выбранном платформенном профиле; произвольный XFF не становится доверенным адресом. Реальные заголовки платформы ещё проверяются на стенде.
6. **Origin/сессии — сохранены.** Один `APP_URL`, secure cookies, текущие роль/статус/филиал и nonce CSP. Регистрация выключена. Нужен отдельный staging-проект со стабильным deployment: `VERCEL_ENV=production` означает стабильный адрес этого тестового проекта, **не production CRM**. Preview не получает БД/Blob. Автоматические Git-deploy отключены явной конфигурацией.
7. **Доступ — ручной bootstrap владельца.** Добавлена интерактивная cloud-команда без password arguments, публичного endpoint и общего seed-пароля. Агент не создавал постоянных Local/cloud администраторов.
8. **Публичная приёмка — не выполнена.** HTTPS/вход обоих кабинетов/расписание/состав/параллельная посещаемость/повтор после commit и reload/конфликты/квитанции после нового deployment/отключение аккаунта/CSP/байтовые лимиты/измерения cold и warm/SLO/soak проверяются на реальной платформе. Публичную ссылку фиксируем только после deployment и приёмки.
9. **Облачные копии и переезд — не выполнены.** Нужны согласованная копия SQL и байтов документов, manifest с storageKey/размером/SHA-256, сохранность незавершённых намерений и практический restore в другую БД/store. Автоматический offsite cloud backup/export в этой итерации не реализован: destination/доступ/RPO/RTO не предоставлены. Локальный SQL+filesystem restore этого не доказывает. При переезде на VPS останавливаем записи, разрешаем неизвестные попытки, проверяем копию/сверку и переносим файлы с прежними storageKey; параллельной записи нет.

## Подготовить ресурсы

Все следующие действия пока ожидают подключения аккаунтов. Создаются только **отдельные ресурсы вымышленного staging**, не ресурсы с настоящими клиентами.

1. Vercel-проект: Node.js 22.x, поддерживаемая платформой patch-версия проверяется при cloud-приёмке; стабильный HTTPS-адрес в `APP_URL`. В шаблоне регион Functions — `fra1`, PostgreSQL желательно рядом.
2. Отдельный Neon-проект/БД `lotos_crm_staging`. Не использовать `neondb_owner` как runtime.
3. Административной процедурой создать `lotos_migrator` и `lotos_runtime`, разные случайные 64-символьные hex-пароли. Обе — LOGIN без SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS и без членства в привилегированной роли. Migrator владеет отдельной БД/схемой; runtime имеет только CONNECT, USAGE, DML таблиц приложения и USAGE/SELECT последовательностей, не владеет таблицами и не меняет схему.
4. Отозвать PUBLIC CREATE на схему и лишний PUBLIC CONNECT на эту отдельную БД. Default privileges задаются **для объектов migrator**. После миграций проверить реальные grants, в том числе чтение `_prisma_migrations` для readiness. Если провайдер/тариф не позволяет это настроить — остановить публикацию, не подставлять owner URL.
5. Настроить `ALTER ROLE lotos_runtime SET statement_timeout = '10s'`. Не отправлять произвольный startup GUC через PgBouncer. Проверить фактическое значение через новую pooled-сессию: `cloud:verify` требует `10s`.
6. **Сейчас пропустить файловое хранилище:** `DOCUMENT_STORAGE=disabled`, не задавать `BLOB_STORE_ID`/`BLOB_READ_WRITE_TOKEN`/`DOCUMENTS_DIR`. Только при отдельном будущем решении включить квитанции понадобится private store. [Private Blob](https://vercel.com/docs/vercel-blob/private-storage).

## Конфигурация и команды владельца

Шаблон: `infra/env/.env.vercel.staging.example`. Владелец вручную создаёт `.env.vercel.staging.local` вне Git, **0600**, без symlink. Загрузка не использует shell expansion, ошибки не печатают credentials.

В Vercel добавить server-only переменные шаблона только для стабильного deployment отдельного staging-проекта. `DIRECT_URL` и `CLOUD_DATABASE_DIRECT_HOST` остаются в приватном операторском файле, не в runtime. Не использовать `NEXT_PUBLIC_*` для секретов, не переносить GAS/SESSION keys и не включать debug/endpoint overrides. При текущем `disabled` не задавать Blob store/token или `DOCUMENTS_DIR`: валидатор отклонит неоднозначную конфигурацию.

Под Node.js 22, из корня проекта:

```bash
npm ci --ignore-scripts
npm run db:generate
npm run cloud:check:local
npm run cloud:migrate
npm run cloud:verify
```

`cloud:check:local` — проверка параметров без подключения. `cloud:migrate` — existing migrations отдельной direct-ролью. `cloud:verify` при отключённых квитанциях проверяет только SQL identity/least-privilege флаги/timeout/миграции, без filesystem/Blob. `cloud:storage:init` сейчас **не выполнять**: она запрещена при `disabled` до создания объектов. Эти команды не создают CRM-администратора и не переключаются на Local/GAS при ошибке.

**Администратора создаёт владелец**, пароль вводится скрыто в интерактивном терминале:

```bash
npm run cloud:bootstrap
```

Аккаунты тренеров создаются через проверенные административные сценарии. Cloud-команды ещё не выполнялись на настоящих ресурсах.

После подключения CLI, настройки environment и успешного `cloud:verify`:

```bash
vercel link
vercel deploy --prod --local-config infra/vercel.staging.json
```

Перед подтверждением `link` проверить, что выбран **новый staging-проект**, не рабочий проект CRM. `--prod` нужен для стабильного адреса именно этого отдельного тестового проекта. Build выполняет `cloud:check` и Webpack-сборку, без миграций. Конфигурация не лежит в корневом `vercel.json`, чтобы не менять существующие deployment автоматически. `.vercelignore` исключает env/XLSX/локальные артефакты; CLI не загружает их в build. [CLI config](https://vercel.com/docs/cli/global-options), [Git deployment settings](https://vercel.com/docs/project-configuration/git-configuration).

Не считать deployment завершённым по сборке. Проверяются настоящий сертификат/live/ready, оба кабинета на телефоне/компьютере, реальные SQL/IP/CSP, повторы/конфликты и отзыв доступа. При `disabled` дополнительно проверяются отсутствие файловых элементов/запросов и FEATURE_DISABLED для прямых файловых маршрутов. Настроить внешние alerts для доступности/ошибок/квот; dashboard без уведомления владельцу недостаточен. Согласовать RPO/RTO и выполнить offsite SQL restore. Если позже включаем документы, отдельно необходимы файловое резервирование/restore и приёмка хранилища. Только затем закрывать этап 12 для согласованного объёма; этап 13 требует отдельной приёмки и разрешения на данные/переключение.

## Ограничения бесплатного теста

Vercel Hobby предназначен для **личного некоммерческого использования**; рабочая CRM клуба не получает автоматически право на этот тариф только из-за небольшого числа клиентов. Для временного личного теста использовать исключительно вымышленные данные; перед реальной эксплуатацией уточнить применимость тарифа и выбрать подходящий платный план либо VPS. Бесплатные квоты приложения, БД и Blob проверяются отдельно. Непрерывная доступность и unlimited storage не обещаются.

Источники, проверенные 9 октября 2026 года: [Vercel Hobby](https://vercel.com/docs/plans/hobby), [лимиты Functions](https://vercel.com/docs/functions/limitations), [private Blob](https://vercel.com/changelog/vercel-private-blob-is-now-generally-available), [Blob SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk).

## Что нужно от владельца

- Подключить Vercel к рабочему чату либо самостоятельно авторизоваться в CLI, не передавая токен/пароль в переписке.
- Выбрать/подтвердить отдельный проект PostgreSQL для **вымышленного staging**, без реальных клиентов и XLSX. Private store сейчас не нужен.
- Создать первого администратора самостоятельно. Существующая ручная команда для Local: `npm run auth:bootstrap:local` под Node.js из `.nvmrc`; она не создаёт администратора облачного стенда.
- Публичный запуск, эксплуатационное восстановление и переключение production проверяются отдельно. Файл не закрывает этапы 10/12/13.
