# Выпуск Лотос CRM

Этот порядок рассчитан на совместимую миграцию схемы 12. `setupSchema()` только добавляет недостающие листы, колонки, текстовый формат дат/времени и предупреждающие защиты. Она не пересчитывает оплаченные занятия. Скрипт можно запускать повторно.

## 0. Подготовка и точка возврата

1. Назначьте окно выпуска без ручного редактирования финансовых колонок Google Sheets.
2. Сделайте полную копию рабочей таблицы. Запишите текущие ID версий GAS и BFF, чтобы код можно было откатить независимо от данных.
3. На копии зафиксируйте число строк и суммы как минимум для `Клиенты`, `Платежи`, `Журнал занятий` и `Посещения`.
4. Подготовьте отдельные активные учётные записи admin и coach для smoke-test. Для проверки блокировки можно подготовить отключённого coach; скрипт не меняет статус аккаунтов.

## 1. Автоматические проверки

Из чистого checkout с Node.js 22:

```bash
npm ci
npm run release:check
```

Команда последовательно выполняет typecheck, все автоматические тесты, ESLint, проверку форматирования и production build. Выпуск прекращается при любой ошибке.

Перед выкладкой проверьте локальные серверные переменные:

```bash
npm run verify:gas
```

Эта команда проверяет только `.env.local`. Равенство секрета с Script Properties опубликованного GAS нужно подтвердить отдельно.

## 2. GAS и совместимая миграция на копии

1. Загрузите текущий `backend/Code.gs` в тестовый Apps Script, связанный с копией таблицы. **До публикации** подключите сервис `Sheets` и выполните `verifyAtomicAccounting()` по инструкции ниже, затем создайте новую неизменяемую версию Web App.
2. В Script Properties GAS задайте `GAS_HMAC_SECRET` длиной не менее 32 символов. В environment тестового BFF должно быть строго то же значение; `apiKey` больше нигде не задаётся и не передаётся.
3. Запустите `setupSchema()` из редактора Apps Script. Ожидаемый результат: `Schema 12 is ready`.
4. Запустите `setupSchema()` повторно. Результат должен быть тем же, заголовки не должны дублироваться.
5. Сравните зафиксированные до миграции остатки `totalLessons` и `remainingLessons`, платежи и посещения. Миграция не должна менять значения или число исторических строк.
6. Под admin выполните `auditLessonLedger` для всех филиалов. Сначала изучите каждое расхождение; исправление выполняйте только отдельной подтверждённой `repairLessonLedger` с причиной.
7. Проверьте, что колонки `date` и `time` листа `Расписание` имеют текстовый формат, а финансовые колонки `Клиенты` получили предупреждающую защиту.

Для новой базы первого администратора создавайте только через `setupInitialAdmin()`. Для существующей базы выполните принудительный сброс старого хеша:

1. Запустите `npm run hash-password` и введите новый временный пароль.
2. Временно задайте в Script Properties `BOOTSTRAP_ADMIN_USERNAME` и `BOOTSTRAP_ADMIN_PASSWORD_HASH`.
3. Для новой базы вызовите `setupInitialAdmin()`, для существующей — `resetBootstrapAdminPassword()`.
4. Убедитесь, что оба временных свойства удалены. Не храните открытый пароль в таблице, репозитории или журнале выпуска.

## 3. Production GAS

1. Повторите резервную копию непосредственно перед миграцией.
2. Убедитесь, что production BFF уже поддерживает HMAC-envelope либо подготовлен к немедленному переключению. `GAS_HMAC_SECRET` в Script Properties и BFF должен совпадать.
3. Опубликуйте проверенную версию `Code.gs` как новую версию GAS Web App; не заменяйте код старой версии без точки возврата.
4. Выполните `setupSchema()` на production-таблице и получите `Schema 12 is ready`.
5. Повторите контроль числа строк, остатков и read-only сверку журнала. При расхождении остановите выпуск до BFF.

## 4. BFF/Next.js

В production environment должны быть заданы:

- `GAS_WEBAPP_URL` новой опубликованной версии;
- тот же `GAS_HMAC_SECRET`, что в Script Properties;
- отдельный `SESSION_SECRET` не менее 32 символов;
- `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN`;
- при необходимости `GAS_TIMEOUT_MS=30000`.

Разверните только артефакт, прошедший `npm run release:check`. После переключения не удаляйте предыдущий BFF deployment и GAS version до завершения контроля следующего дня.

## 5. Автоматизированный smoke-test

Smoke-test выполняет только вход, чтение сводок, проверку 403 и выход; платежи, посещения и карточки он не меняет. Передайте секреты через защищённые environment variables CI/терминала:

```bash
SMOKE_BASE_URL=https://crm.example.ru \
SMOKE_ADMIN_USERNAME=... \
SMOKE_ADMIN_PASSWORD=... \
SMOKE_COACH_USERNAME=... \
SMOKE_COACH_PASSWORD=... \
npm run smoke
```

## Самостоятельная регистрация тренера

- Ссылка для тренера: `https://<ваш-домен>/register`; на экране входа есть «Зарегистрироваться». `localhost:3001/register` доступен только на компьютере, где работает сервер.
- Сначала опубликуйте обновлённый `backend/Code.gs`, затем обновите Next.js/BFF. Используются существующие колонки схемы 12; новая версия схемы не нужна. Старый GAS не поддерживает `registerCoach` и не создаст аккаунт.
- Публичный `POST /api/auth/register` принимает логин, пароль и `requestId`. BFF проверяет формат, ограничивает попытки и передаёт GAS только scrypt-хеш. Открытый пароль не хранится в таблице, браузерном хранилище или логах.
- GAS под общим lock добавляет одну строку `Users`: роль `2`, пустой `branchId`, статус `Ожидает подтверждения`. Поля роли, филиала и статуса из браузера игнорируются. Cookie входа не создаётся и не меняется.
- Войдите как admin → «Тренеры» → «Новые заявки». Выберите филиал и нажмите «Подтвердить доступ»: кнопка последовательно сохраняет филиал и активирует аккаунт, только после подтверждения первого шага. Если второй шаг не удался, заявка остаётся ожидающей подтверждения; обновите список и повторите действие. До подтверждения аккаунт не может войти или читать CRM.
- После подтверждения заявка исчезает из блока новых заявок, а тренер появляется в общем списке. Даже если отдельной строки в листе «Тренеры» нет, активный или отключённый аккаунт отображается карточкой с логином и филиалом. При наличии связи по `userId` имя и контакты берутся из профиля, без дублирования карточки. Несвязанные старые профили сохраняются; их можно явно объединить с нужным логином. Автоматически связывать людей по имени или создавать выдуманные профили интерфейс не пытается. Это объединение отображения, не миграция таблицы.
- Филиал, отключение/восстановление входа и смена пароля доступны внутри карточки в блоке «Управление тренером». При подтверждении регистрации пароль менять не нужно. Отключение входа не удаляет тренера из списка. Если удалить сведения из связанного профиля, аккаунт остаётся в списке с отключённым входом; история сохраняется.
- Повтор регистрации с занятым логином не меняет существующий пароль, роль или статус. Ответ одинаковый для нового и уже существующего логина. При потерянном подтверждении форма предлагает повторить тот же запрос, не создавая второй аккаунт.
- Для production обязателен общий Upstash Redis: отдельные от входа лимиты регистрации — 3 попытки на IP+логин и 10 на IP за 15 минут. При недоступности лимитера регистрация закрывается безопасной ошибкой; обращение к нему ограничено тайм-аутом 5 секунд. Хостинг должен подставлять доверенный IP, а не принимать произвольный `X-Forwarded-For` от клиента. Для публичного сайта дополнительно настройте WAF/защиту от ботов на `/api/auth/register`.

Перед выпуском на копии проверьте: регистрация нового тренера, отказ входа до подтверждения, повтор после потери ответа, отсутствие дублей и сохранность пароля занятого логина; затем назначение филиала, подтверждение администратором и обычный вход в тренерский кабинет. Проверьте 403 для административных действий и другого филиала. Автоматизированный smoke-test выше не создаёт аккаунты: этот сценарий выполняется отдельно на тестовой базе.

Дополнительные проверки:

- `SMOKE_DISABLED_COACH_USERNAME` и `SMOKE_DISABLED_COACH_PASSWORD` — вход существующего отключённого coach должен вернуть 401;
- `SMOKE_REQUIRE_LEDGER_CLEAN=1` — read-only аудит всех клиентов должен вернуть ноль расхождений.

После smoke-test вручную проверьте в браузере под admin и coach:

1. Оба селектора филиала перезагружают дашборд, расписание и справочники.
2. Coach видит только свой филиал, не видит финансы и получает 403 при прямом запросе.
3. Повторяющееся занятие открывается на правильную дату; сохранение одной и той же отметки повторно не списывает занятие.
4. Повторная отправка одного платежа с тем же `requestId` не создаёт вторую запись.
5. Архивный клиент отсутствует в roster, но остаётся в истории и финансах; удалить можно только пустую ошибочную карточку.
6. При количестве клиентов больше 100 доступны серверный поиск ребёнка, полные финансы и корректная пагинация абонементов.

### Оформление административного кабинета

Начальная загрузка администратора включает публичные поля аккаунтов тренеров
в `coachAccounts` вместе с профилями. Раздел не отправляет дополнительный
`getUsers` при открытии; ручное обновление и обновление после изменения доступа
сохраняются. Данные аккаунтов не выдаются coach. Для оптимизации обновите GAS
deployment; со старым GAS останется прежний дополнительный запрос.

Для групповой записи из формы создания занятия обновите GAS и выполните
`setupSchema()`: в расписании добавляется `clientIds`. Новая операция
`createLessonWithClients` проверяет весь список (до 100 клиентов) до записи,
сохраняет назначение клиентов и состав группы под общим mutation-lock.
В случае ошибки записи выполняется компенсирующий откат; это не транзакция Sheets.
Старый GAS отклонит новую операцию до создания занятия. Старые занятия без
`clientIds` сохраняют прежнюю выборку посещаемости; новые группы показывают
только записанных клиентов. Проверьте запись 20 клиентов, смену филиала/секции,
повтор с тем же requestId и ошибку записи в середине группы.

Список выбора тренера в занятии объединяет профили и подтверждённые аккаунты
выбранного филиала. Связь определяется только по `userId`, а не по совпадению имён.
Подтверждённый аккаунт без профиля отображается по логину. При возвращении в раздел
«Тренеры» последний полученный список остаётся видимым во время обновления;
этот снимок доступен только текущей административной сессии и не заменяет
серверную проверку прав. Первый вход в форму занятия при отсутствии снимка
загружает аккаунты отдельным запросом, не загружая список клиентов заранее.

Админка использует общую с кабинетом тренера визуальную систему: белую навигацию,
нейтральный рабочий фон, бирюзовые акценты и компактные панели. Сводка показывает
серверные показатели клиентов и занятия на сегодня из загруженного расписания.
Незагруженные показатели отображаются как «—», а не как нулевые значения.
Дополнительных запросов для оформления нет; права доступа и схема GAS не менялись.
Проверьте узкий экран, выбор филиала, переходы из сводки и сохранение посещаемости.

### Проверка устойчивости кабинета тренера

Эта версия меняет и Next.js, и `backend/Code.gs`. Сначала выпустите GAS,
затем Next.js: повтор сохранения опирается на постоянный `requestFingerprint`
в журнале, а не только на пятиминутный кеш. Новых колонок к схеме 12 не требуется.
Для новых отметок «отсутствовал» и подтверждений неизменной отметки появляются
строки `attendance_confirmation` с нулевым движением занятий — это нормально.

На копии таблицы проверьте:

- у coach только дашборд и расписание, без управления филиалами и создания занятий;
- при 503 проверки сессии есть повтор проверки, а при 401 доступ закрывается;
- без сети и при неполном ответе API не появляется ложное подтверждение сохранения;
- выбранные отметки и неподтверждённый запрос сохраняются при закрытии модалки,
  переключении раздела и восстановлении экрана в рамках открытой сессии;
- после полного обновления страницы черновик не сохраняется: откройте занятие
  и проверьте фактические отметки перед новой отправкой;
- после исправления отметки и очистки кеша старый `requestId` не отменяет исправление;
- отключённый coach и попытка работы с другим филиалом по-прежнему получают отказ;
- кнопки восстановления не отправляют посещения автоматически.

Резервные экраны не заменяют мониторинг и резервную копию. Записи через
`SpreadsheetApp` всё ещё используют компенсационный откат, а не настоящую
транзакцию нескольких листов. Полную остановку GAS или сбой самого отката
интерфейс исправить не может: нужна сверка журнала администратором.

### Проверка ускорений и количества запросов

Оптимизация карточки клиента (схема остаётся **12**):

- Сначала опубликуйте новую версию `backend/Code.gs`, затем Next.js. Изменения
  совместимы: старый `getClientHistory` продолжает работать, новый клиент
  передаёт `includeAudit: true`. Только при отсутствии этого контракта на старом
  GAS он отдельно запрашивает сверку; явная ошибка сверки не запускает повторный запрос.
- При открытии карточки — один запрос вместо двух. `Клиенты`, `Платежи` и
  `Журнал занятий` читаются по одному разу и используются историей и сверкой.
  Ошибка сверки показывается отдельно и не скрывает подтверждённые платежи.
- При обычной успешной оплате — один `recordPayment` вместо оплаты и трёх
  последующих чтений. Интерфейс применяет подтверждённые сервером суммы,
  остатки, платёж и запись журнала; сам деньги и занятия не начисляет.
  Если история ещё загружается, GAS старый, изменён фильтр или нужна перепагинация
  сортировки по оплате, выполняется соответствующее дополнительное чтение.
- `recordPayment` читает три бухгалтерских листа по одному разу; отдельные чтения
  заголовков и повторные чтения журналов убраны. Права проверяются по актуальному
  `Users` при каждом вызове. Полная сверка перед записью и общий lock сохранены.
- Повтор платежа возвращает текущие остатки, а не старый ответ кеша. Подтверждённая
  операция определяется по долговечному `requestId` в платежах и журнале. При
  потере HTTP-ответа используется одно объединённое чтение; неподтверждённая
  попытка повторяется с тем же ключом. Ключ сохраняется при переключении карточек
  в текущем представлении, но не переживает перезагрузку браузера: после неё
  сначала проверьте историю, не создавайте новый платёж вслепую.
- Общая сверка предварительно разделяет журнал и платежи по клиентам вместо
  повторного обхода полных листов для каждого клиента. Номера физических строк
  в диагностике сохранены. Это оптимизация расчёта в памяти, не индекс Google Sheets.

На копии таблицы проверьте обычную оплату, двойной клик, потерю ответа,
повтор старого `requestId` после нового платежа, смену клиента/сессии и сбой
обновления истории. Платёж не должен удваиваться, чужая карточка не должна
меняться, а ошибка обновления не должна изображаться отказом сохранения.
В логах дополнительно есть `payment.snapshot_loaded`. Количество запросов
проверено автоматическими тестами; реальную задержку GAS измеряйте после выкладки.
Новых миграций для этих оптимизаций нет. Атомарная запись посещений не включается
этим изменением. Платежи, корректировки, исправление сверки и создание клиента
теперь требуют сервис `Sheets` и выполняются атомарно, как описано ниже.

### Обязательная атомарная запись бухгалтерских операций

`recordPayment`, `recordAdjustment`, `repairLessonLedger` и `createClient`
используют один `Sheets.Spreadsheets.batchUpdate` на операцию. Все изменения
карточки, платежа и журнала применяются одним пакетом; отдельной записи с
компенсационным откатом больше нет. Новые колонки и смена версии схемы не нужны.

**Перед публикацией новой версии GAS:**

1. Сначала на копии проекта откройте **Services → + → Google Sheets API**,
   выберите **v4**, идентификатор **Sheets**, нажмите **Add**.
   При стандартном Google Cloud project отдельно включите Google Sheets API
   в Cloud Console. Для автоматически созданного проекта это делает добавление сервиса.
2. Из редактора GAS выполните `verifyAtomicAccounting()` и подтвердите разрешения.
   Ожидаемый ответ: `Atomic accounting is ready`. Проверка читает только ID
   таблицы через API, не меняет карточки, платежи или журнал.
3. Выпустите тестовую версию Web App. Проверьте оплату, корректировку, подтверждённое
   исправление сверки, создание клиента с оплатой и без неё. Проверьте отказ API
   до записи и повтор с тем же `requestId` при потере ответа после сохранения.
4. После проверки повторите настройку сервиса и проверку доступа на рабочем GAS,
   затем опубликуйте новую версию Web App. Настройка только в тестовой копии
   не подключает сервис в рабочем проекте.

Это не опциональный флаг: без сервиса `Sheets` перечисленные новые записи
отклоняются с `SCHEMA` до изменения таблиц. Старый небезопасный способ записи
автоматически не включается. Чтение данных не требует Advanced Sheets service.

Если ответ API потерян, GAS **не удаляет строки и не откатывает карточку**:
пакет мог уже сохраниться. Повторяйте неподтверждённую операцию с прежним
`requestId`, а не с новым. Платёж определяется по постоянным строкам платежа
и журнала; корректировка и исправление — по маркеру журнала. Создание клиента,
включая первую оплату, сохраняет нулевой маркер `client_creation` с хешем запроса
в том же пакете. Он предотвращает повторную карточку после истечения кеша;
изменённый запрос с тем же ключом отклоняется. Маркер не начисляет занятия,
не является оплатой и сам по себе не запрещает удаление пустой ошибочной карточки.
После удаления маркер остаётся, чтобы поздний повтор не восстановил карточку.

Значения API передаются литералами (`stringValue`), не формулами. Платежи записываются
по именам заголовков, поэтому перестановка колонок не смешивает суммы и идентификаторы.
Меняются только нужные ячейки клиента. Общий lock, свежая проверка `Users`
и сверка журнала сохранены. Атомарность пакета не блокирует ручные правки или
сторонний API: не редактируйте учётные колонки параллельно в обход CRM.
Исторические расхождения этот выпуск автоматически не устраняет.

Справка: [подключение Advanced services](https://developers.google.com/apps-script/guides/services/advanced),
[атомарность spreadsheets.batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate).

Дополнительный проход оптимизации интерфейса:

- `AdminWorkspace` загружается отдельным JS-модулем только после входа admin;
  coach не загружает административную оболочку и её элементы выбора филиала.
- История и аудит открытой карточки зависят от ID ученика, а не от нового объекта
  после обновления списка. После бухгалтерских операций они обновляются явно;
  серверная сверка при записи не изменена.
- Создание занятия не запрашивает список учеников, пока не открыт необязательный
  выбор клиента. Неудачная загрузка видна и повторяется только по действию пользователя.
- Поиск игнорирует изменения только в крайних пробелах; начальная загрузка
  абонементов не ждёт 250 мс. Пагинация защищена от двойного клика и запоздалого
  ответа предыдущего поиска.
- Даты недели мемоизированы: открытие модалки не запускает повторную фильтрацию
  неизменившегося расписания.

Локальный замер одинаковых production-сборок Webpack до/после разделения:
сумма уникальных `script src` из стартового HTML — 954 472 → 862 500 байт;
gzip-сумма тех же файлов — 292 425 → 262 466 байт (−10,2%). Это сравнение
артефактов, включая общие runtime/polyfill-скрипты, **не замер браузерного трафика
или времени загрузки на реальном устройстве**. Код admin загружается позже при
входе admin; неизменённые библиотеки по-прежнему составляют большую часть размера.

Кабинет тренера оформлен отдельным рабочим пространством: боковая навигация
на компьютере, компактные вкладки на телефоне, сводка по расписанию филиала,
календарь недели и переход к ближайшему занятию. Сводка не изображает сохранённую
посещаемость: она считает только занятия из загруженного расписания. Даты и недели
переключаются локально; открытие занятия по-прежнему загружает актуальный roster.
При недоступной начальной загрузке календарь и нулевые показатели не выдаются за
отсутствие занятий. При ошибке повторной загрузки сохраняются предупреждение и
последнее подтверждённое расписание. Автоматической отправки отметок нет.

У coach обычный путь без фоновых запросов к административным экранам:

| Действие                                                        | Запросы к BFF / GAS                                               |
| --------------------------------------------------------------- | ----------------------------------------------------------------- |
| Вход                                                            | 1 `auth/login` / 1 `getAuthUser`                                  |
| Восстановление открытой сессии после перезагрузки страницы      | 1 `auth/session` / 1 `getCurrentUser`                             |
| Первая загрузка кабинета или ручное обновление                  | 1 `getBootstrapData`, без листа `Тренеры`                         |
| Переключение дашборд ↔ расписание, выбор даты, отметки кнопками | 0                                                                 |
| Открытие занятия                                                | 1 `getLessonRoster`, свежее чтение, без кеширования остатка в BFF |
| Сохранение                                                      | 1 `recordBulkAttendance` на каждые 100 изменённых отметок         |
| Неподтверждённый результат / таймаут сохранения                 | 0 дополнительных автоматических запросов                          |

Эта таблица описывает нормальный путь на актуальном GAS. Совместимость с очень
старой версией GAS включает дополнительные чтения после `NOT_FOUND`; обновите
GAS первым. Скрытые административные экраны ничего не предзагружают. Краткий
каждый подписанный вызов GAS теперь читает актуальную строку `Users`, включая
чтения справочников и повторы сохранения. Второго удалённого вызова авторизации
нет: эта проверка выполняется внутри того же запроса. Приватный кеш ответов
Next.js отключён для всех ролей: другая серверная реплика больше не может
выдать устаревшие права или десятиминутный список клиентов. Кеш справочников
GAS остаётся после проверки доступа, с общей версией `READ_CACHE_VERSION`.
Переменные `CRM_READ_CACHE_*` больше не управляют выдачей CRM-ответов.

Сверка посещений использует индексы только в рамках текущего запроса под lock,
не кешируя финансовое состояние между запросами. Открытие roster читает
`Расписание` и `Клиенты` по одному разу. Сохранение читает четыре бизнес-листа
по одному разу и по-прежнему выполняет полный контроль журнала и платежей
выбранных учеников. На тестовой группе 100 учеников среди 2000 клиентов
расчёт журнала и проверка платежей посещают 200 строк вместо 800 000, плюс одноразовое
построение индексов. Это уменьшение работы в памяти, **не обещание такого же
ускорения сетевого запроса**.

Для измерения после выкладки:

1. В DevTools Network проверьте число запросов и `Server-Timing: crm;dur=…`.
2. В серверных логах BFF смотрите `gas.request.completed` с `durationMs`.
3. В Apps Script смотрите `mutation.lock_acquired`, `attendance.snapshot_loaded`,
   `authorization.completed`, `attendance.validated`, `attendance.written`, `mutation.finalized` и
   `request.finished`. В логах только длительности, число отметок и технический
   статус, без содержимого отметок и персональных данных.
4. Замерьте несколько последовательных сохранений на копии таблицы, включая
   первый холодный вызов. Если BFF/GAS занимает большую часть времени вне
   этапов чтения/записи, дальнейшее ускорение требует отдельного решения по
   хранилищу/развёртыванию, а не удаления защиты доступа или `flush`.

### Подтверждённые остатки и атомарное сохранение

Успешное сохранение возвращает для каждого ученика `client.remainingLessons`,
`client.totalLessons` и `client.status`. Дашборд обновляет видимые остатки из
этого ответа без повторного запроса. Запоздалая сводка, начатая до сохранения,
не перезаписывает подтверждённый остаток. Со старым GAS без этих полей сводка
перезагружается один раз; некорректные дополнительные поля не отменяют уже
подтверждённое сохранение. Повтор посещения возвращает текущий остаток из
таблицы, а не снимок пятиминутного кеша ответа.

Для атомарного изменения `Клиенты` и `Журнал занятий` добавлен отдельный режим.
Он **не включается автоматически** и не требует новых колонок:

1. На копии проекта Apps Script добавьте сервис **Google Sheets API v4** с
   идентификатором `Sheets`. Для стандартного Cloud project включите также
   Google Sheets API в Cloud Console; подтвердите необходимые разрешения.
2. Задайте Script Property `ATTENDANCE_ATOMIC_WRITES=true` именно в GAS.
3. Выпустите новую версию Web App и проверьте отметку, исправление и повтор
   с тем же `requestId`. Остаток, история и журнал должны измениться вместе.
4. Проверьте сбой связи и повтор неподтверждённого запроса: не должно появиться
   второго списания. Локальные тесты моделируют и отказ до записи, и потерю
   ответа после успешной записи; реальный сервис нужно проверить отдельно.
5. Только после smoke-test повторите настройку на рабочем GAS и выпустите Next.js.

Режим отправляет один `Sheets.Spreadsheets.batchUpdate` с изменёнными ячейками
и строками журнала. Значения передаются как литералы, не формулы. Общий lock,
актуальная авторизация, сверка и постоянные маркеры requestId сохраняются.
Ошибка API не запускает запасную запись или откат: ответ мог потеряться уже
после успешного коммита. Интерфейс сохраняет прежний requestId для повтора.
Если режим включён без сервиса `Sheets`, запрос отклоняется до любой записи.

Без этого свойства остаётся совместимый пакетный `SpreadsheetApp` с откатом;
он не даёт гарантии атомарности при остановке GAS или отказе самого отката.
Атомарность нового режима действует **на пакет до 100 отметок**, не на всю
группу из нескольких пакетов. Ручные правки и сторонние API не участвуют в
script lock — не редактируйте учётные колонки в обход приложения.

Справка: [Advanced Sheets service](https://developers.google.com/apps-script/advanced/sheets),
[атомарность spreadsheets.batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate).

## 6. Переключение и откат

После успешного smoke-test переключите production-трафик на новый BFF deployment. Если ломается только BFF, верните предыдущий deployment. Если ошибка в GAS, верните предыдущий URL/версию GAS вместе с совместимым BFF. Добавленные схемой колонки и листы не удаляйте во время аварийного отката; восстановление значений выполняйте только из резервной копии после сравнения журналов.

## 7. Контроль следующего рабочего дня

Сверьте за период выпуска:

- число и суммы строк `Платежи` с журналом типа `purchase`;
- все изменения остатка с `Журнал занятий`;
- посещения с типами `attendance` и `attendance_correction`;
- отсутствие повторов `requestId` с разным `requestFingerprint`;
- `Журнал администрирования` на неожиданные ручные правки;
- ошибки 401/403/409/503 и rate-limit без персональных данных в логах;
- работу входа активного coach и отказ отключённому coach со старой и новой сессией.

Только после этой проверки удаляйте временные учётные записи и закрывайте окно выпуска.
