# Этап 4: авторизация и серверные права PostgreSQL

Дата: 7 октября 2026 года. Ветка: `migration/self-hosted`.

Продолжение: [справочники этапа 5](CATALOG_POSTGRES.md) уже подключают создание/редактирование клиентов, филиалы и профили тренеров. Этот отчёт фиксирует проверки этапа 4; утверждения о ещё не подключённых справочниках ниже описывают его исходный срез. Актуальные границы и проверки справочников — в новом отчёте.

## Результат и границы

Реализован отдельный PostgreSQL-режим существующего Next.js API: вход по логину, выход, проверка серверной сессии, ожидающий аккаунт тренера, активация/отключение, назначение филиала, сброс пароля, завершение всех сессий и привязка существующей карточки. Новый режим проверяется настоящим Prisma/Better Auth, а не только mock-тестами. Интерфейс и контракты `/api/auth/*`, `/api/crm` сохранены.

**Локальная техническая приёмка этапа 4 завершена.** На итоговой версии повторены production-сборка, регрессии, PostgreSQL integration, реальные HTTP-запросы и браузерные сценарии двух кабинетов. Это не объявление готовности всей CRM или production: перенос остальных модулей и эксплуатационные условия перечислены ниже.

**Это ещё не перенос всей CRM.** В PostgreSQL пока нет создания/редактирования справочников, полного расписания, посещаемости, платежей и файлов. Неперенесённый разрешённый запрос получает явный SERVICE_UNAVAILABLE: сервер не обращается к GAS и не выдаёт фиктивный успех или пустую историю.

`npm run dev` остаётся legacy-командой. Новый режим запускается явно через `npm run dev:postgres`. Production, рабочая таблица, реальные пользователи и пароли не менялись. Реальный администратор локально автоматически не создавался: логин и пароль выбирает владелец через защищённую CLI-команду.

## Разделение backend

Существующий catch-all route выбирает backend по **серверному** CRM_BACKEND:

- `gas` или отсутствие настройки — прежний режим; прежние тесты и возможности сохраняются.
- `postgres` — только PostgreSQL-сессии и новые сервисы. Ни старый JWT, ни browser auth/role/branchId не являются доверенным контекстом.
- Неизвестное значение — закрытый отказ 503, не случайное переключение на GAS.

Режим не выбирается URL-параметром или полем JSON. PostgreSQL-конфигурация проверяется до подключения. Старые cookies `lotos_crm_session` не принимаются; при новом входе/выходе они также очищаются. Новая HttpOnly cookie Better Auth использует namespace `lotos`.

## Проверка доступа

[access.ts](../lib/server/postgres/access.ts) разрешает cookie через Better Auth, затем читает актуальные Session + User + Branch из PostgreSQL. Проверяются:

1. Серверная сессия существует и принадлежит этому пользователю.
2. Срок действия не истёк.
3. Аккаунт active, логин существует.
4. authVersion сессии равна текущей authVersion пользователя.
5. Тренеру назначен существующий, неархивный филиал.
6. Действие разрешено актуальной роли. Область чтения тренера задаётся сервером из текущего филиала, а не присланным branchId.

Cookie cache выключен. GET проверки не обновляют сессию скрытой записью; сессия имеет серверный срок 8 часов. На каждом защищённом запросе разрешения проверяются заново. Роль может измениться после выдачи cookie — старый admin-интерфейс не даёт права выполнить admin-запрос.

Перед административной записью контекст повторно проверяется внутри транзакции под блокировкой строки актёра. Целевой аккаунт также блокируется до проверки роли. Только coach-аккаунты доступны этим admin-операциям; они не являются способом сбросить пароль или отключить администратора. Управление собственным паролем администратора/аварийное восстановление должно иметь отдельную согласованную процедуру, не публичный bootstrap backdoor.

Новые права создания занятий тренером предусмотрены новой policy, но сервис создания относится к этапу 6. Удаление занятия тренером запрещено. D-01a по области изменения/отмены всё ещё открыто; эти действия не выданы случайно. Legacy-политика GAS не расширялась.

## Подключённые маршруты и действия

| Endpoint / action                         | Реализация                                                                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| POST `/api/auth/login`                    | Username/password через Better Auth, канонический UI-user, только нужные cookies; token/hash/authVersion в JSON не выдаются |
| GET `/api/auth/session`                   | Свежая проверка доступа, существующий контракт authenticated/user                                                           |
| POST `/api/auth/logout`                   | Удаление серверной сессии и очистка cookies, включая уже отозванный аккаунт                                                 |
| POST `/api/auth/register`                 | Только pending coach, без филиала, сессии, admin-прав или вымышленного email; feature flag                                  |
| `getUsers`                                | Безопасные coach-account summaries для администратора                                                                       |
| `assignUserBranch`                        | User + linked Coach + исторические CoachBranch в одной транзакции; прошлые занятия не перемещаются                          |
| `activateUser`                            | Только после назначения действующего филиала; не создаёт карточку человека по совпадению имени                              |
| `deactivateUser`                          | Отключение доступа, серверное время, version bump и удаление всех сессий                                                    |
| `resetCoachPassword`                      | Новый хеш Better Auth, version bump и удаление всех сессий                                                                  |
| `revokeUserSessions`                      | Явный отзыв всех устройств без отключения аккаунта                                                                          |
| `linkCoachUser`                           | Точная связь существующей карточки и coach-аккаунта одного филиала, без повторной привязки к чужой карточке                 |
| `getCurrentUser`                          | Минимальный канонический пользователь, без credential-полей                                                                 |
| `getBootstrapData`, `getDashboardSummary` | Минимальные реальные scoped-чтения для загрузки существующих кабинетов; не реализация всех каталогов и отчётов              |

В разделе «Тренеры» для PostgreSQL-аккаунтов появилась кнопка «Завершить сессии» с подтверждением. Она не показывается в legacy GAS, который не поддерживает новое действие. Остальные существующие кнопки управления доступом используют тот же API-контракт.

Форма входа поддерживает отправку Enter, корректные autocomplete/name для password manager и доступное сообщение об ошибке. Повторный вход сохраняет существующее разделение кабинетов, а перезагрузка страницы заново проверяет серверную сессию.

Произвольный `auth.handler` **не** смонтирован. Raw endpoints Better Auth (`update-user`, `update-session`, `change-password`, `sign-up/email`, reset endpoints и т. п.) не открыты браузеру. Все поддерживаемые действия проходят через проверенный адаптер CRM. Supabase Auth параллельно не используется.

## Отзыв и гонки

Изменение пароля, отключение, повторная активация, смена филиала/привязки и явный отзыв увеличивают серверную authVersion и удаляют сессии в одной транзакции. Повторная активация не оживляет старые cookies.

При входе версия аккаунта фиксируется **до** проверки пароля. После Better Auth сервер снова проверяет выданную сессию и версию. Если пароль сбросили в процессе проверки, старые credentials не могут получить cookie новой версии: промежуточная сессия удаляется, cookie не передаётся клиенту. Гонка проверена отдельным тестом.

На этапе 4 используется общий advisory lock только для редких операций управления аккаунтами/публичной регистрации/bootstrap. Он не является проектом блокировки всей CRM; будущая посещаемость и платежи должны использовать собственные строки клиентов и проверенные версии.

## Атомарность и повторы

Административное изменение, увеличение версии, удаление сессий, аудит и MutationRequest коммитятся вместе. Отказ аудита откатывает также доступ и сессии — это проверено на настоящем PostgreSQL.

Ключ подтверждения — actorId/requestId. Fingerprint строится по семантическим данным, включая действие; для пароля используется HMAC, не случайная соль нового password hash и не открытый SHA-256 plaintext. Аудит содержит имена изменённых полей, а не пароль/хеш.

После новой операции старый повтор деактивации, активации, назначения филиала, сброса пароля или отзыва сессий возвращает подтверждение, но не изменяет более новое состояние. Повтор проходит текущую авторизацию. Другие данные с тем же ключом дают CONFLICT.

В PostgreSQL-режиме API-клиент сохраняет ключ и семантические данные попытки управления аккаунтом после сетевого сбоя/5xx/неполного success. Параллельные одинаковые отправки объединяются; изменение неподтверждённых данных блокируется. Пароли не пишутся в localStorage/sessionStorage или журналы. Попытки хранятся **только в памяти текущей сессии** и очищаются при смене пользователя/выходе; восстановление такого административного черновика после reload ещё не реализовано. После reload сначала сверять состояние, а не считать неизвестный исход доказанным отказом. Это ограничение не скрывается как гарантия end-to-end восстановления.

Для анонимной pending-регистрации добавлена RegistrationAttempt: долговечный HMAC-key/fingerprint, связанный с созданным пользователем. Аккаунт, credential, подтверждение и аудит создаются атомарно. Повтор после последующей активации не создаёт второй аккаунт и не выдаёт сессию.

HTTP 408 также считается неопределённым результатом, а не доказательством отказа записи. Найденный дефект сброса ключа после такого таймаута сначала воспроизведён тестом, затем исправлен. Браузерная проверка теряет ответ **после успешного коммита** сброса пароля и подтверждает, что повтор использует прежний requestId: в БД остаётся один маркер и версия аккаунта не увеличивается второй раз.

Сейчас fingerprints используют BETTER_AUTH_SECRET. Его ротация должна быть согласована с неопределёнными попытками и сохранёнными маркерами: новый секрет не должен становиться поводом отправить старую операцию с новым ключом. Отдельный стабильный ключ идемпотентности/версии ключей можно добавить перед production-операционной ротацией. При несовпадении текущая реализация отказывает CONFLICT, не выполняет операцию повторно.

## HTTP и ограничения входа

- POST требует точного Origin настроенного APP_URL; cross-site fetch отклоняется. JSON-only предотвращает form POST bypass. Тестовый curl должен также передавать корректный Origin.
- Реальные байты тела ограничены **до** JSON.parse: auth 16 КБ, подключённые CRM-операции 64 КБ. Content-Length не является единственной проверкой. Объект, payload и поля проверяет Zod; браузерные role/status/authVersion/passwordHash отвергаются.
- Ошибки переводятся в типизированные публичные коды, без SQL/строк подключения/password payload. Ошибка БД не превращается в «сессия действительна». Логи runtime содержат только маршрут, статус и operational metadata.
- AuthRateBucket использует атомарный PostgreSQL UPSERT: счётчик и TTL меняются одним запросом. Окно 15 минут; login — 8 на пару и 40 на IP, registration — 3 на пару и 10 на IP. Успешный вход не обнуляет общий бюджет; разные username начинают создавать ключи только после проверки IP-бюджета. Устаревшие временные записи удаляются.
- Ни Redis, ни Upstash для PostgreSQL-авторизации не нужны. Встроенный process-local limiter Better Auth отключён, потому что все публичные поддерживаемые auth endpoints ограничены общим DB-хранилищем. Открывать новые auth endpoints без этого адаптера нельзя.
- Raw X-Forwarded-For/X-Real-IP не доверяются. По умолчанию IP = unknown, то есть общий консервативный бюджет. `TRUSTED_PROXY=caddy` разрешается только после приватного размещения Next за Caddy и проверки, что Caddy **перезаписывает** `X-Lotos-Client-IP`, а внешний клиент не попадает напрямую в Node. Один флаг без инфраструктурного ограничения не доказывает доверие к proxy.

Общая защита slow requests, edge limits, TLS, CSP, monitoring и реальное размещение proxy относятся к подготовке hosting, а не считаются выполненными этими тестами.

## Старые пароли и регистрация: решения не выдумываются

Старые GAS scrypt-хеши распознаются только для безопасного отклонения. Вход их не принимает и не перезаписывает автоматически. На вымышленном legacy-аккаунте проверены отказ входа и последующий успешный вход после контролируемого admin-сброса на Better Auth.

Сервис сброса готов; **выбор массовой процедуры переноса старых паролей ещё требует ответа владельца**. Импорт реальных аккаунтов не выполнялся. Email для username-login не требуется.

Публичная pending-регистрация реализована как возможность, но **по умолчанию выключена**: `COACH_REGISTRATION_ENABLED=true` — явное включение. В тестах она включается только на вымышленных аккаунтах. Production-необходимость пока не считается согласованной (D-09); до ответа не включать её автоматически.

## Локальный запуск

На закреплённом Node 22, с Docker-доступом:

```bash
npm run db:local:up
npm run db:migrate:local
npm run auth:bootstrap:local
npm run dev:postgres
```

bootstrap спрашивает логин, имя и пароль дважды в интерактивном терминале. Пароль не отображается, не передаётся аргументом/env и не пишется в файл. Минимальная длина первого admin-пароля — 12 символов; выбирайте длинный уникальный пароль через password manager. После появления любого admin повтор запрещён, в том числе при отключённом admin; аварийное восстановление — отдельная процедура, не второй bootstrap.

Открывать APP_URL из `.env.db.local`, обычно `http://localhost:3001`. Перед запуском остановить свой старый dev-процесс через Ctrl+C, если он занимает порт. Команда сама его не убивает. Новый local-режим читает только отдельную DB-конфигурацию, явно выставляет CRM_BACKEND=postgres, чистит legacy credentials в дочернем процессе и слушает loopback. Она не запускает доступный всему интернету сервер и не создаёт реальные staging/production.

Local-база по-прежнему не содержит автоматического seed рабочих пользователей/клиентов. Филиалы/карточки будут подключены на следующем этапе; без созданного филиала ожидающему тренеру нельзя выдать доступ. Не заполнять это пробелом через production-проект или угадыванием существующих людей.

## Миграции и проверка

Новая четвёртая миграция добавляет два служебных хранилища и проверку credential identity. Прежние три миграции не переписывались. Всего теперь 21 модель. Local/test bootstrap-роли остаются изолированными superuser для разработки; production должен получить отдельные least-privilege роли до выпуска.

```bash
npm run typecheck
npm test
npm run test:postgres
npm run test:auth:postgres
npm run lint
npm run format:check
npm run build -- --webpack
npm run test:auth:http
npm run test:auth:browser
npm run security:secrets
```

- 253 unit/regression теста: прежние 248 + 5 тестов frontend account retry, включая HTTP 408.
- 28 PostgreSQL foundation тестов, включая совместимость предыдущей схемы и backfill.
- 35 интеграционных auth-тестов: bootstrap race, роль/филиал/статус/версии, old replay, credentials, pending, CSRF, реальные ограничения запросов, атомарность/rollback, rate limit, отключённая регистрация, legacy-хеши и отказ сервиса.
- 4 проверки **настоящего production Next HTTP-сервера** с отдельной временной БД: admin/coach session/bootstrap, pending activation/reset, отсутствие доступа через старый JWT/raw endpoints и logout/CSRF.
- 4 браузерных сценария Chromium через Playwright 1.63.0: admin-вход/выход и reload; мобильный coach, свой филиал и прямой запрещённый API; отзыв сессий из админки с проверкой другого браузера; повтор сброса пароля после потери подтверждения коммита. Проверяется отсутствие pageerror, включая ошибки React/MST. Мобильная ширина — 390 px. Это целевые проверки авторизации, не полный E2E остальных модулей CRM.

HTTP suite требует предварительной сборки. Она проверяет свободный тестовый порт, запускает только собственный loopback-процесс, завершает только свой PID и удаляет свою одноразовую DB. Не подключается к существующему пользовательскому серверу. `test:auth:browser` выполняет те же 4 HTTP-проверки плюс 4 браузерные — всего 8, без двойного подсчёта. Вымышленные credentials создаются в одноразовой БД; persistent browser state, HAR и файлы с паролями не сохраняются. Внешние запросы браузера блокируются.

Для браузерного прогона сначала установить Chromium: `npx playwright install chromium` (Linux также требует системные зависимости Playwright). В текущем workspace браузер загружен в игнорируемый `.tools/playwright`; wrapper выбирает его автоматически. На чистом CI используются стандартная установка и `npx playwright install --with-deps chromium`.

Итоговая сборка через Webpack проверена; `release:check` и CI используют тот же проверенный bundler. Ограничение default Turbopack в текущем sandbox и Google Fonts остаются в [ENVIRONMENTS.md](ENVIRONMENTS.md). CI включает PostgreSQL auth и HTTP/browser suites, но запуск workflow на GitHub/deployment не выполнялся. Gitleaks используется с redaction; не является абсолютным доказательством отсутствия любых секретов. В sandbox часть unit-тестов требует разрешения на дочерние Node-процессы: итоговый разрешённый прогон выполнен целиком, без пропуска проверки часовых поясов.

Повторный npm audit после добавления Playwright показывает прежние 12 high предупреждений из этапа 3; новых предупреждений не добавилось. Они не скрываются и не исправлялись `--force`. До публичного выпуска — адресные исправления, полноценный staging, роли БД, резервное восстановление, полный browser regression и закрытие зависимых бизнес-решений.

Технические источники: [Better Auth server API](https://better-auth.com/docs/concepts/api), [сессии и cookie cache](https://better-auth.com/docs/concepts/session-management), [username plugin](https://better-auth.com/docs/plugins/username). Детали проверялись по установленным версиям и собственным интеграционным тестам.
