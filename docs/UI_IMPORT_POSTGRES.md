# Этапы 9–10: интерфейсы и повторяемый тестовый импорт

Локальная приёмка: 8 октября 2026 года. Явный PostgreSQL, Local и одноразовый Test. Не production-релиз.

Последняя доработка этапа 9: расширенное recovery всех 21 защищённых SQL-операций и конкретная [матрица приёмки](UI_ACCEPTANCE_MATRIX.md). Ниже отражено текущее состояние, а не только первоначальные 404 проверки.

## Результат и границы

Доработано согласованное ядро обоих интерфейсов: каталоги, календарь, состав, посещаемость, учёт и документы. Создан операторский test-importer предоставленного XLSX с dry-run, SQL-транзакцией, устойчивыми ID и безопасным карантином. Это не универсальный production-importer любой таблицы.

Постоянный apply исходного XLSX не запускался. После просьбы «доделай» выбран и озвучен консервативный вариант для тестового набора: четыре старых занятия только архивом, без догадок о тренерах/составе. Local проверен: база пустая, девять миграций есть, активного администратора нет. Для apply требуется интерактивный bootstrap владельцем; пароль агенту не передаётся. Подробная последовательность — [операторская процедура](TEST_IMPORT_RUNBOOK.md). Запись на одноразовой БД не является переносом настоящих пользователей.

## Этап 9

Существующие внешний вид и MobX/MST сохранены. Загрузка, ошибка чтения и пустой список различаются; подтверждённая запись и ошибка обновления списка сообщаются отдельно. Версии защищают от устаревших изменений. Запоздавшие ответы после смены аккаунта/карточки не подменяют текущие данные.

Календарь и создание используют `Europe/Moscow`, независимо от зоны браузера. Местная дата филиала отделена от UTC-интервала занятия. Временной статус сравнивает настоящие instants; часы обновляются локально без опроса API.

### Восстановление операций

- В обоих кабинетах появилась панель собственных попыток после reload. Список не возвращает пароли, суммы и персональные payload. Данные очищаются вместе со сменой сессии; сервер заново проверяет доступ.
- Для всех 21 согласованных защищённых SQL-операций нормализованный запрос сохраняется приватно на сервере до основной транзакции: справочники, создание/изменение/отмена/удаление допустимого занятия, назначения, учёт и управление доступом. Посещаемость и файлы используют собственные recovery-процедуры. Намерение — не подтверждение; результат подтверждает отдельный неизменяемый SQL-маркер.
- Восстановление использует исходные данные/ключ. Подтверждённый запрос признаётся выполненным без второго создания/начисления и без применения старого результата поверх нового.
- Закрытие не удаляет подтверждённые записи. Общая блокировка ключа и повторная проверка состояния внутри writer запрещают позднюю запись закрытой незавершённой попытки. После acknowledgement/close приватный payload очищается, fingerprint остаётся.
- Подтверждение получения результата выполняется отдельно. Его сбой оставляет безопасную запись в панели, а не отменяет выполненную операцию. Автоматической повторной отправки по таймеру нет.
- Посещаемость сохраняет собственную ранее реализованную серверную recovery-логику и версии отметок. Старый повтор не отменяет новое исправление; пакет остаётся атомарным.
- Квитанции восстанавливаются по собственному намерению и проверенным байтам приватного файла. После SQL-сбоя записанный файл можно привязать после reload без нового ключа/файла. Если байты отсутствуют, нужен исходный файл; хеш/размер запрещают подмену. Старый повтор не возвращает старую квитанцию поверх новой.
- Закрытие файлового намерения не удаляет файлы. Сверка остаётся read-only; очистка/срок хранения относятся к эксплуатации.

Пароли не сохраняются в browser storage или общей таблице recovery. Для создания доступа/сброса после reload подтверждённый результат можно проверить без пароля. Незавершённая попытка требует повторного ввода исходного пароля; HMAC-отпечаток отвергает другую семантику. Если исходный пароль неизвестен, попытка явно закрывается перед новой операцией. Поле очищается после результата. Девятая миграция запрещает credential-ключи в JSON на уровне SQL.

Исправлены два воспроизведённых UI-дефекта: recovery-панель тренера подписана на готовность bootstrap, а формы редактирования/корректировки/продления вложены в Dialog Root профиля. Добавлены клавиатурные кнопки карточек/занятий и сортировки. API отвергает запоздавший ответ прежней сессии; root store также не применяет старые mutation-ответы. Последующий 4xx не сбрасывает ключ ранее неопределённой попытки.

Исторические JSON-отметки импорта доступны администратору отдельным read-only архивом карточки, не создают новые списания и не превращаются в выдуманные текущие отметки. Массовые операции серии, изменение старых составов и исправления архивных клиентов не разрешены автоматически. D-08 не менялся: статус клиента остаётся ручным.

## Этап 10

1. Offline XLSX-разбор ограничивает архив/XML/размеры, отвергает формулы и внешние связи; нормализует ID и Excel-даты без локали браузера. Исходник не изменяется.
2. План явно содержит `testOnly`, `Europe/Moscow`, исключение старых финансов и политику disabled/reset. Credential-колонки исключаются до SQL-плана; ручной план с password/secret/token/signature отклоняется.
3. Dry-run не создаёт Prisma-клиент и не пишет SQL. Проверяет ограниченную структуру и арифметику исходного журнала, возвращает очищенные количества/карантин. Все SQL-связи дополнительно проверяет транзакционный writer; dry-run не является exhaustive SQL-проверкой.
4. Apply доступен только Local/Test и явно выбранному действующему admin. Staging/production отклоняются до записи. CLI требует `--apply` и `--actor`.
5. Old→new ID зависят от namespace, вида сущности и старого ID. Одна транзакция включает справочники, подтверждённые экземпляры/составы/отметки, opening credits, архив, provenance, аудит и маркер.
6. Повтор того же источника/плана возвращает исходный отчёт без перезаписи дальнейших изменений CRM. Изменение плана в занятом namespace или тот же источник под другим namespace дают CONFLICT. Нельзя менять namespace ради обхода проверки.
7. Остатки подтверждаются исходным журналом. Импортный opening balance явно обозначает количественные остатки, а не вымышленную покупку. Старые посещения не списывают занятия повторно.
8. Владение занятием задаётся явным `coachBindings`, не совпадением имени. Текущая отметка требует точных даты/экземпляра/участия; неполные данные остаются immutable legacy-архивом/карантином.
9. Старые сессии/GAS/JWT не переносятся. Старый admin сопоставляется выбранному новому владельцу; coach-аккаунты создаются выключенными без копирования хешей. Затем нужны контролируемый сброс и активация.
10. По решению владельца старые платежи исключены. Старые деньги карточек сохраняются как свидетельство источника, но не выдаются за новую подтверждённую выручку/баланс. Новая тестовая бухгалтерия начинает с нулевых денежных полей; новые платежи работают штатно.

Восьмая миграция добавила файловый recovery-payload/abandoned, private mutation drafts и immutable import batches/records. Девятая расширяет действия recovery и добавляет credential-флаг/SQL-запрет паролей в payload. Обе применены только Local/Test; предыдущие миграции не переписывались. Upgrade проверен отдельно, включая старое файловое намерение без payload: оно не объявляется автоматически resumable.

### Проверка предоставленного XLSX

SHA-256: `557b6ec1f5f607f9ee49615213cbd7bcbcb1936432f19deb451512b9626ab061`.

На одноразовом PostgreSQL проверены запись и повтор: 3 клиента, 1 филиал, 1 исходный профиль; 2 coach-аккаунта отключены для сброса. Старый admin сопоставлен тестовому владельцу. Остатки сохранены **2/4, 7/8, 6/8**.

Без утверждённых привязок все 4 старых занятия проверены как карантин, 7 исторических JSON-отметок сохранены архивом без новых списаний. Это **не четыре работающих импортированных занятия в календаре**. Для текущей просьбы «доделай» озвучен архивный вариант по умолчанию; точные назначения не угадываются. Постоянный apply ждёт безопасного bootstrap администратора в пустой Local-базе.

В листе платежей нет записей. 20 000 ₽ в карточках не объявляются подтверждённой выручкой. XLSX содержит личные поля/хеши, исключён из Git; raw-план нельзя публиковать. В CI используются fictional fixtures, отсутствие приватного XLSX явно отмечается skipped.

В этом источнике нет receiptUrl. Перенос Drive-байтов не проверен: источник с квитанциями отклоняется с требованием отдельного плана файлов. Импорт старых повторяющихся серий требует явного плана экземпляров; создание новых серий приложением не доказывает такой импорт.

Старые requestId/журналы сохраняются как provenance, но не становятся native API-ключами с другими fingerprint/authVersion. Выполнение старых GAS-запросов на новой базе не обещается.

## Команды

Использовать закреплённый Node 22 согласно [ENVIRONMENTS.md](ENVIRONMENTS.md).

```bash
npm run db:migrate:local
npm run dev:postgres

# Нормализованный тестовый dry-run без SQL-записи:
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08

# Сначала интерактивный bootstrap владельца и приватная копия Local:
npm run auth:bootstrap:local
npm run db:backup:local

# После проверки dry-run, архивный вариант без --bindings:
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08 --actor YOUR_ADMIN_LOGIN --apply

# Независимая сверка сохранённых данных, без SQL-записи:
npm run import:test:local -- --source "База данных.xlsx" --namespace gas-test-2026-10-08 --verify

# Для согласованных назначений добавить --bindings /private/path/bindings.json.
```

Bindings: `{ "coachBindings": { "OLD_LESSON_ID": "coach:OLD_COACH_ID" }, "rosters": { "OLD_LESSON_ID": ["OLD_CLIENT_ID"] } }`. Допускается `user:OLD_COACH_USER_ID` для явно согласованного создания профиля. Это образец структуры, не назначения реальных строк.

Прежняя `npm run import:dry-run -- "База данных.xlsx"` остаётся строгим read-only анализом и может возвращать exit 2 на исторических неоднозначностях. Её `readyForImport: false` не противоречит отдельному проверенному test-importer.
