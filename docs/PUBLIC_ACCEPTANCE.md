# Публичная приёмка согласованного staging

Это процедура следующего шага, не результаты уже выполненной публичной проверки. Объём: RELEASE_SCOPE.md. Подключение: SUPABASE_STAGING.md / VERCEL_STAGING.md.

## Подтвердить площадку

Записать отдельные Supabase/Vercel project IDs, постоянный APP_URL и точную ревизию. Только вымышленные staging-данные. До migrate/seed проверить отсутствие рабочих клиентов в выбранном проекте. Установить runtime/migrator/backup роли, CA/hostname verification, statement_timeout=10s; cloud:verify должен пройти на реальном endpoint. Администратора создаёт владелец вручную.

## Проверить приложение на настоящей платформе

| Проверка | Ожидаемый результат |
| --- | --- |
| HTTPS, /api/health/live, /api/health/ready | Корректный сертификат, 200, no-store; private DB details не раскрываются |
| Вход администратора и тренера, desktop/mobile | Кабинет соответствует актуальной роли/филиалу |
| Чужой филиал и административный API от тренера | Отказ, без приватных данных и предметной записи |
| День/неделя, пустой день, московские даты при другом timezone браузера | Нет сдвига даты и автоматического переноса старого урока на сегодня |
| Создание занятия с пустым/непустым составом | Точный подтверждённый состав; неизвестные связи не расширяются на весь филиал |
| Посещаемость, исправление, два параллельных запроса на последний остаток | Атомарная запись, один расход, версии/конфликт вместо перезаписи |
| Потеря ответа после commit и reload | Восстановление исходного ключа, без второго платежа/списания/занятия |
| Платёж/корректировка/история/сверка | Точные деньги и согласованный журнал; подтверждённая запись не теряется при ошибке refresh |
| Отключение аккаунта, смена филиала, сброс пароля | Старые сессии/страницы не получают прежний доступ |
| DOCUMENT_STORAGE=disabled | Нет файлового UI/network; прямые авторизованные файловые запросы получают FEATURE_DISABLED |
| CSP, no-store и platform proxy headers | Свежий nonce, чужой nonce не принимается; platform IP проверен без spoofed XFF |
| Новый deployment/cold start | SQL intents/маркеры сохранены, pooler/таймауты работают |

Записывать агрегаты и IDs; не пароли, cookies, SQL-параметры или персональные выгрузки. Реальные транзакции после потери ответа сверяются на выделенных вымышленных сущностях.

## Внешняя копия и восстановление

Для текущего disabled-профиля резервируются SQL и содержащиеся в нём подтверждения/попытки, без обещания файлового backup. После выбора хранилища настроить job под read-only backup-role; credentials держать на runner, не в Vercel runtime или Git. Копия должна иметь checksum, timestamp и идентичность источника.

Практически скачать копию из внешнего хранилища, восстановить в **другой** изолированный проект/БД, сверить количества/остатки/историю/intents и выполнить вход/контрольные сценарии. Сохранить время восстановления. Проверить отказ повреждённого архива. Не перезаписывать живую БД для репетиции.

Настроить alerts на внешний HTTPS/live/ready, SQL failures/timeouts, pool/connection limits, возраст внешней копии и неуспешные jobs. Проверить фактическое получение одного тестового уведомления в выбранном владельцем канале. Канал и отправка ещё не настроены.

## Длительная нагрузка

До прогона согласовать целевые concurrency, длительность и SLO. Измерять cold/warm отдельно, p50/p95/p99, ошибки, SQL round trips и общее число соединений при нескольких Vercel processes. Не запускать нагрузку на рабочие данные. Короткий локальный session-smoke и внутрипроцессный benchmark не заменяют эту проверку.

Этап 12 закрывается только после реальных доказательств для согласованного объёма. Этап 13 выполняется по CUTOVER_RUNBOOK.md после фиксации площадки/данных/окна.
