# Простой первый запуск CRM

Решение владельца, 10 октября 2026: приоритет — работающие клиенты, тренеры, расписание, посещаемость и оплаты. Упрощаем запуск и количество активных компонентов; не переписываем проверенные бизнес-операции и не обещаем «никогда не упадёт».

## Одна рабочая цепочка

| Часть                | Сейчас                                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------- |
| Приложение           | Один Next.js-проект `lotos-crm-staging` на Vercel                                                       |
| Данные               | Одна отдельная staging PostgreSQL в Supabase, не рабочие Sheets                                         |
| Вход                 | Существующий Better Auth, логин/пароль и две роли; без Supabase Auth/SDK/Data API                       |
| Runtime              | Prisma + pg, один переиспользуемый connection на serverless process, Transaction pooler 6543            |
| Первый администратор | Ручной SQL Editor fallback `npm run cloud:bootstrap:sql`; локальный libpq/psql оставлен для диагностики |
| Квитанции/файлы      | Выключены (`DOCUMENT_STORAGE=disabled`); Blob/store/ключи не нужны                                      |
| Выпуски              | Ручной deploy отдельного staging, без Git autodeploy и без переключения рабочей CRM                     |

Bootstrap больше не держит Node/Prisma SQL-соединение во время ввода владельца. Preflight — отдельное короткое read-only соединение; создание — один SQL-скрипт с transaction lock, повторной проверкой отсутствия admin и атомарными user+credential+audit. Better Auth hash вычисляется до подключения; plaintext пароль не отправляется в PostgreSQL. Локальный `postgres:17-bookworm` используется как одноразовый psql-клиент, не как второй сервер БД. Автоматического скачивания образа/переинициализации БД/повтора записи нет.

## Что сохраняем

- Оплаты и расход занятий сохраняются вместе с подтверждением операции. Повтор после потерянного ответа не должен создавать второй платёж или списание.
- Пароли хешируются, сессии можно отозвать, тренер ограничен актуальным филиалом. TLS остаётся с проверкой CA и hostname.
- Несовместимые изменения получают конфликт, а не тихую перезапись. Журнал подтверждённых операций сохраняется.
- Ошибка подключения — понятный отказ, без переключения на Sheets, другой env или другую роль. Ограниченные таймауты заменяют бесконечное ожидание.

Это базовая корректность CRM, а не дополнительный «банковский» контур. Новых сервисов, SDK, очередей, ключей Blob и платных ресурсов не добавляем. Не удаляем историю, миграции, self-hosted подготовку или ранее реализованные функции.

## Обычный следующий шаг владельца

В терминале VS Code/WSL, не в SQL Editor:

```bash
cd /home/ury/projects/lotos_crm
export PATH="/home/ury/projects/lotos_crm/.tools/node/bin:$PATH"
npm run cloud:bootstrap:check
npm run cloud:bootstrap:sql
```

Команда `cloud:bootstrap:sql` локально спрашивает логин, имя и пароль, затем создаёт игнорируемый Git приватный файл `.private/supabase-first-admin.sql` с необратимым Better Auth hash. Выполните **весь файл один раз** в SQL Editor выделенного staging-проекта Supabase. Успех подтверждается строкой `LOTOS_BOOTSTRAP_COMMITTED`. После read-only проверки входа файл нужно удалить. Операция сохраняет transaction lock, проверку отсутствия admin, атомарные user+credential+audit и не включает Data API/Supabase Auth.

Прежний `cloud:bootstrap` для Supabase теперь намеренно завершается до подключения с `BOOTSTRAP_SQL_EDITOR_REQUIRED`: повторять подтверждённый нестабильный WSL/Docker → Session pooler write-path запрещено. Для Local и других явно поддержанных профилей поведение команды не меняется.

Первая команда только читает роль/БД/число admin/доступность lock. Вторая требует TTY и спрашивает логин, имя и скрытый пароль 12–200 символов с повтором. Не передавай пароль аргументом и не присылай его в чат. Результат создания подтверждается только маркером после COMMIT. Если admin уже есть — создание запрещено. После неопределённой ошибки сначала выполняется read-only check; автоматического повтора нет. Используется уже имеющийся Docker/локальный образ; Linux/WSL daemon — `/var/run/docker.sock`, без remote Docker context.

## Когда можно сказать «работает»

После создания владельцем первого admin — публикация и проверка именно на Vercel: live/ready, вход обоих кабинетов, создание клиента/занятия, посещаемость, оплата, reload и повтор запроса без дубля. Затем backup/restore и наблюдение по [PUBLIC_ACCEPTANCE.md](PUBLIC_ACCEPTANCE.md). Локальные тесты и успешный bootstrap не заменяют эти доказательства.

Supabase менять сейчас не обосновано: штатные миграции из Vercel и read-only libpq-подключение прошли; первичный локальный Node/Prisma timeout всё ещё не имеет доказанного низкоуровневого корня. Если реальный HTTP runtime на Vercel воспроизведёт проблему, фиксируем конкретный сценарий и пересматриваем транспорт/площадку по результатам, без очередного слепого сброса БД.
