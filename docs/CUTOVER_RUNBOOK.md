# Этап 13: контролируемое переключение и передача

**Статус: процедура подготовлена, переключение не выполнено.** Vercel сейчас предназначен только для отдельного вымышленного staging. Ни эта инструкция, ни успешные локальные тесты не разрешают автоматически переносить реальные данные, отключать GAS или создавать администратора. Постоянный Local-admin создаёт владелец.

## Условия GO / NO-GO

До начала назначить владельца решения и оператора. Переключение не начинается, пока не выполнены все условия:

- Есть публичный staging и пользовательская приёмка обоих кабинетов по [VERCEL_STAGING.md](VERCEL_STAGING.md) либо [STAGING_RUNBOOK.md](STAGING_RUNBOOK.md).
- Выбрана рабочая площадка и допустимый для CRM тариф. Облачный валидатор сейчас разрешает только staging: подстановка `APP_ENV=production` в Vercel намеренно не работает.
- Утверждены состав переноса, судьба спорных исторических занятий, связанные аккаунты/тренеры, дата отсечения, стартовые остатки и политика старых платежей. История платежей тестового источника исключается только согласно ранее данному решению, не удаляется из исходника.
- Владелец выполнил безопасный bootstrap в нужном окружении, определены реальные пользователи. Пароли/хеши старого формата не считаются автоматически совместимыми.
- Есть проверенная версия кода и миграций, успешный release image/deployment, внешние alerts, согласованные RPO/RTO и практическое восстановление SQL **и** документов из внешней копии.
- Остаточные advisories/HTTP-SLO/soak и спорные UI/бизнес-сценарии закрыты либо явно приняты ответственным владельцем с ограничениями и сроком. Сборка не является таким решением.
- Согласованы окно остановки записей, пользовательское сообщение и план отката. Есть отдельное разрешение владельца на реальное переключение.

Любое невыполненное условие — NO-GO. Не обходить его ослаблением валидатора, owner-ролью runtime или параллельной записью в Sheets/PostgreSQL.

## Выполнение в согласованное окно

1. **Разобрать неизвестные операции.** Проверить сохранённые попытки и серверные подтверждения; повторять только прежний ключ и прежние данные. Подтверждённый платёж/отметку/квитанцию не создавать заново. Если результат не удалось установить, зарегистрировать исключение и остановить переход.
2. **Остановить записи в старой версии.** Предупредить пользователей, закрыть мутации на сервере, проверить отказ прямого API. Скрытые кнопки недостаточны. Пока не отключать доступ к старому источнику для сверки.
3. **Снять исходную копию.** Сохранить все необходимые листы/заголовки, файлы, метаданные и контрольные суммы. Записать время/ревизию, проверить читаемость и внешнее размещение копии. Не публиковать XLSX/хеши в Git или staging.
4. **Финальный dry-run и импорт.** Проверить согласованный namespace/source/immutable plan. Затем применить импорт в выбранную рабочую БД штатной проверенной процедурой. Сверить количество сущностей, old→new ID, составы, тренеров, каждый остаток, документы и карантин. Не придумывать недостающие платежи и не исправлять расхождения молча.
5. **Сохранить целевую точку восстановления.** После импорта, до новых записей — согласованная копия SQL/файлов и manifest. Проверить права runtime/migrator/backup и готовность хранилища.
6. **Переключить один источник записи.** Настройки выбранной рабочей площадки переводятся на PostgreSQL штатным профилем. Проверить HTTPS, origin/cookies/CSP, ready и вход владельца. Старый GAS не должен одновременно принимать мутации.
7. **Проверить оба кабинета.** Сначала read-only сверка; затем согласованные контрольные операции на обозначенных тестовых сущностях. Проверить расписание/состав/пакет посещений/исправление/повтор/платёж/приватный файл/отзыв доступа. Не выполнять необозначенные тестовые платежи на реальных клиентах.
8. **Возобновить работу и наблюдать.** Только после GO владельца. Наблюдать доступность, ошибки, неизвестные попытки, latency, квоты/диск, состояние backup job; время наблюдения задаётся в плане приёмки.

В журнале перехода фиксировать только необходимые агрегаты/ID, не credentials или персональные выгрузки.

## Если переход не прошёл

- **До новых записей в PostgreSQL:** после проверки, что целевая версия не принимала изменения, можно согласованно вернуть единственный старый источник записи и расследовать дефект на копии. Данные импортированной БД не удалять автоматически.
- **После новых записей:** остановить запись, сохранить обе стороны и список операций. Простое включение GAS теряет новые данные и не является безопасным откатом. Нужны проверенный forward-fix либо отдельная сверка/процедура обратного переноса; решение принимает владелец.
- Rollback приложения к прежнему коду допустим только при совместимости со схемой и данными. Не выполнять destructive down-migration после появления новых данных. Для изменений схемы использовать проверенный совместимый план.
- Повреждённую копию/неполный manifest не использовать как основание для удаления живых данных. Восстановление выполняется в отдельную среду и проверяется до смены адресов.
