Этап 2. Переделать авторизацию и пароли
1. Убрать apiKey из тела запроса BFF → GAS.
2. Оставить один механизм доверия: HMAC-подписанный envelope с timestamp и nonce.
3. Сначала обновить GAS: проверять только HMAC. Затем обновить BFF и перестать отправлять apiKey.
4. Убрать быстрый HMAC/SHA-256 для паролей.
5. Перенести проверку пароля в Node/BFF на crypto.scrypt; в таблице хранить только формат вида scrypt$....
6. Для существующих старых хешей выбрать безопасную миграцию:
   - рекомендовано: принудительный сброс паролей;
   - альтернатива: разовая миграция при первом успешном входе.
7. Ограничение входа перенести в BFF:
   - лимит по комбинации IP + логин;
   - отдельный лимит по IP;
   - одинаковый ответ при неверном логине и пароле;
   - надёжное хранилище счётчиков или защита на уровне WAF/хостинга.
Критерий: нельзя создать первого администратора через публичный endpoint, нельзя заблокировать известный аккаунт одним логином, хеши не подбираются быстро офлайн.

Этап 4. Завершить целостность конкурентных операций
Уже исправлено многое: мутации CRM под lock, посещаемость пишет только изменённые колонки, платежи идемпотентны. Осталось закрепить правила.
1. Все новые мутации проводить только через общий mutation lock.
2. Любое изменение баланса, статуса или аккаунта снабжать requestId.
3. Не перезаписывать строку целиком, если меняются 1–3 колонки.
4. Для ручных изменений в Google Sheets добавить правило: финансовые и абонементные колонки не редактируются вручную.
5. Добавить аудит изменений для ручных администраторских корректировок.
Критерий: параллельные платёж, посещение и архивирование не теряют данные и не создают двойных записей.
